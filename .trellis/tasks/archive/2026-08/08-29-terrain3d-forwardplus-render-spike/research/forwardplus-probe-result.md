# Terrain3D 1.0.2 / Godot 4.7.1 Forward+ probe result

## Result

The historical all-black Terrain3D surface did not reproduce on the current
Windows target. A real non-headless isolated run rendered the authored
Terrain3D demo material under Godot `4.7.1-stable`, Forward+, D3D12, and an AMD
Radeon RX 9070 XT. The native surface contributed 100% of sampled pixels in the
terrain-only camera, all changed pixels were non-black, and luminance ranged
from `0.1451` to `0.7471`. Hiding Terrain3D produced the expected dark control
frame. Hiding `MouseQuad` did not change the authored result, so it is not the
cause on this runtime.

The accepted logical surface ranged from `-0.3130 m` to `1.5402 m`; the
`TerrainState` epoch, generation, revision, and SHA-256 remained identical
before and after every render/material variant. The authored material and the
bundled minimum shader override both produced finite, non-black, height-varying
frames.

The final retained evidence is
`output/terrain3d_phase0/20260829-173613/`; future reruns use the same
`output/terrain3d_phase0/<timestamp>/` layout generated by
`tests/run_terrain3d_forwardplus_probe.ps1`. The run writes PNG variants,
current-run stdout/stderr/Godot logs, `evidence.json`, and `run-summary.json`.

## Root cause bounded by current evidence

The old black-frame observation has no committed frame/log artifact and cannot
be assigned a current root cause. Terrain3D 1.0.2 remains supportable on the
current engine/GPU target without a vendored addon or binary change.

The probe did expose a separate deterministic initialization defect: the
adapter loaded and deep-duplicated the authored `Terrain3DMaterial` once before
enter-tree and again after enter-tree. Replacing the live resource on Godot 4.7
D3D12 left stale/null material RIDs and emitted repeated
`Parameter "material" is null` RenderingServer errors even though pixels were
visible. The project-side fix caches the exact pre-tree resource and reuses it;
post-enter assignment occurs only if native initialization actually cleared or
replaced the property. The corrected probe has zero shader, GDExtension,
material, texture-array, Terrain3D, or map-import errors in its current-run
logs.

The final runner explicitly selects `--rendering-method forward_plus` and
`--rendering-driver d3d12`, requires all authored/minimum/MouseQuad-hidden
variants plus the exact target renderer, and scans both import and probe logs.
Its summary reports `fatal_log_matches=[]`.

Missing or invalid configured material paths now fail with the stable message
`Terrain3D material is unavailable: <path>`. The deliberate-failure probe
asserts native availability remains false and the fallback mesh plus foundation
remain visible. The focused adapter test also corrects the path and proves the
same pending snapshot recovers with the cached material object assigned to the
native node.

## Regression evidence

- `terrain3d_forwardplus_probe.gd`: authored material, MouseQuad-hidden,
  minimum override, native-absent control, authority fingerprint, and deliberate
  material failure.
- `terrain3d_adapter_test.gd`: explicit native profile, full import, two
  contiguous patches, reset/full resync, stale guards, snapshot-byte parity,
  dressing stability, Jolt native collision enable/disable, and unchanged
  logical terrain.
- Passing focused gates: `construction_site_terrain_test.gd`,
  `terrain_state_test.gd`, `terrain3d_adapter_test.gd`,
  `soil_authority_migration_test.gd`, `soil_interaction_authority_test.gd`,
  `analytic_dig_test.gd`, `excavation_gameplay_test.gd`, and
  `release_candidate_test.gd`.

The full standalone matrix was attempted twice but is not claimed green. A
client-only isolate lacks the repository-level CAN Gateway required by
`can_gateway_e2e_test.gd`; the live working copy cannot load a second Terrain3D
hot-reload DLL while the user's editor owns
`~libterrain.windows.debug.x86_64.dll`, and its unrelated Gateway child exited
before heartbeat. All Terrain3D/terrain/soil/Jolt gates above ran in an isolated
copy with the native DLL loaded successfully.

## Phase 1 interface

Phase 1 may supply a project-owned Terrain3D material through
`Terrain3DAdapter.material_path`. It must remain a `Terrain3DMaterial`, retain
Terrain3D's clipmap/height/control-map vertex contract, and be assigned before
the native node enters the tree. The adapter owns resource caching and must not
replace a live material with a fresh duplicate on the post-enter pass.

The product default remains `terrain_backend="soil_shader"` after Phase 0.
